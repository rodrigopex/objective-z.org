How it works

A build step, not a runtime

The transpiler runs before the compiler. It reads a Clang JSON AST of your Objective-C, resolves every dispatch it can at build time, and emits ordinary .h/.c files that GCC compiles like any other Zephyr source.

Static-first by design

Every existing Objective-C runtime — Apple libobjc, GNUstep libobjc2, ObjFW, mulle-objc — mallocs its dispatch tables, class tables and instances at runtime. That is fine on a phone and wrong on an MCU with 64–512 KB of RAM and no MMU.

Dispatch tables in FLASH

Objective-Z emits const vtable arrays into .rodata, indexed by class_id — zero RAM cost. When the receiver type is known at transpile time, a protocol call collapses into a direct function call.

Objects from slab pools

Instances come from per-class k_mem_slab pools in .bss, auto-sized from AST analysis. No malloc, no fragmentation, no allocator metadata per object.

No dynamic magic

KVO, swizzling, dynamic class creation, associated objects, weak references and message forwarding are gone — they all need unbounded runtime allocation. What remains is what can be resolved at build time: classes, protocols, categories, properties, blocks, ARC.

The landscape

Why not one of the other languages?

Several languages promise better abstractions over C for embedded work. We evaluated each against the reality of building on Zephyr, where the entire ecosystem — kernel, drivers, build system, macros — is C.

Separate compiler

Rust

An amazing language, but adopting it means emigrating, not learning new syntax. The borrow checker rewires how developers think about lifetimes. The toolchain is a separate compiler from Zephyr's, creating two-ABI friction, and every kernel API needs FFI bindings that break on upstream updates. Kernel-level development is effectively off-limits, and binaries are harder to audit for WCET.

Breaks the macros

C++

Looks C-compatible but isn't. Zephyr's macro-heavy API — K_THREAD_DEFINE, K_SEM_DEFINE, DEVICE_DT_DEFINE — relies on C-specific preprocessor behavior; compiling with g++ changes the language under the macros. Beyond that, C++ has fractured into eras: a developer comfortable with C++03 faces a nearly foreign language in C++20/23. It keeps trying to become something else, which is bad for teams rooted in C.

No OOP vocabulary

Zig

The most sympathetic "better C": no hidden control flow, comptime instead of macros, good C interop. But it shares Rust's separate-compiler problem and deliberately does not support OOP — no classes, no inheritance, no method dispatch. Approximating interfaces requires acrobatics the language doesn't enforce.

Different language

Nim

The closest competitor: it also transpiles to C, has --mm:arc for deterministic memory, and a Zephyr wrapper. But despite the C output it is a completely different language — Python-inspired, significant whitespace, its own module and metaprogramming model. Zephyr's C macros don't pass through Nim's FFI cleanly, so bindings must manually replicate what the macros expand to. Its OOP model uses GC'd reference types by default, and the generated C is Nim-idiomatic rather than human-auditable.

Hobbled subset

Swift

The obvious question given Objective-C heritage. Embedded Swift strips runtime reflection and existentials to reach microcontrollers, and has experimental Zephyr integration. But it is still a separate LLVM-based compiler with its own ABI, the embedded subset is experimental, and it disables the very features that make Swift feel like Swift. You get a hobbled Swift instead of full Objective-C lowered to clean C.

No Zephyr support

Ada / SPARK

The establishment answer for safety-critical embedded, with proven formal verification, and it deserves respect. But there is no official Zephyr support — only a proof-of-concept requiring a custom SDK rebuild with GNAT enabled. The language, toolchain and ecosystem are unfamiliar to teams coming from C, and the adoption cost is enormous.

Interpreter + heap

Lua

A tiny interpreter, easy to embed, widely used for IoT scripting. But it is interpreted — every instruction pays a runtime dispatch cost that destroys WCET analyzability, and the VM heap-allocates tables, strings and closures. You can strip it down, but you still pay for an interpreter loop where you need deterministic compiled code. It adds a scripting layer on top of C rather than improving the C itself.

Garbage collector

Go / TinyGo

The garbage collector is a one-line disqualifier for zero-heap, deterministic, ISR-safe embedded systems.

They all share one root cause

A separate compiler (Rust, Zig, Swift, Ada). Broken macro compatibility (all of them — even C++ and Nim). An unfamiliar language model (Rust, Nim, Ada). A hobbled feature subset (Swift). An interpreter with heap allocation (Lua). A garbage collector (Go). Different failures, one cause: each asks the embedded C team to leave C.

Objective-Z doesn't. The developer writes Objective-C — a strict superset of C — and the entire Zephyr API surface, macros and devicetree accessors included, is directly visible and usable in the .m source with zero bindings. The transpiler converts it to plain, auditable C. The compiler only ever sees C. The linker only ever sees C.

No new compiler. No FFI bindings. No interpreter. No garbage collector. No moving target. No unfamiliar syntax. The team gains classes, protocols, ARC-based RAII and deterministic dispatch without leaving the world it already understands.

Head to head

Objective-Z vs C++

C++ is the alternative most embedded teams reach for first, so it deserves the closest look. The short version: comparable speed, materially smaller firmware, and none of the macro or dialect friction.

The macros are the problem

Zephyr's API is preprocessor-driven. K_THREAD_DEFINE, K_SEM_DEFINE and DEVICE_DT_DEFINE depend on C-specific preprocessor and linker-section behavior. Building with g++ changes the language underneath those macros — so the parts of Zephyr you most want to touch are the parts that fight back.

Objective-C is a strict superset of C. The macros expand exactly as they do in C, because the file is C plus objects.

Which C++ does your team know?

C++ has grown into distinct eras. A developer fluent in C++03 meets a nearly foreign language in C++20/23 — different idioms, different ownership vocabulary, different error messages. Every hire and every code review has to negotiate which dialect the codebase speaks.

Objective-C's object model has been stable for decades, and the subset Objective-Z supports is deliberately small: classes, protocols, categories, properties, blocks, ARC. There is no next edition to migrate to.

The output is reviewable

Transpiled C is ordinary C — a named function per method, a const array per vtable, a slab pool per class. A reviewer, a static analyzer, or a certification auditor reads the same code the compiler does.

Template-heavy C++ gives you object code whose shape you infer rather than read.

One toolchain, unchanged

No compiler swap, no CONFIG_CPLUSPLUS, no exception or RTTI configuration, no libstdc++ footprint decisions, no ABI seam between your code and the kernel's. The build gains one Python step and keeps GCC.

Where C++ still wins

  • @synchronized is expensive — 266 cycles against 15, because the RAII OZSpinLock is allocated and freed. The underlying k_spinlock is 15 cycles on both sides; reach for it directly on a hot path.
  • Reference counting costs more — 22 cycles to retain vs 7 for a raw atomic_fetch_add, and 44 vs 17 for a retain/release pair. The gap is a null check plus a real function call.
  • Placement-new from a slab is 2× faster — 105 cycles vs 215. The extra Objective-Z cycles are the init vtable call and the ARC release.
  • Object-array iteration is ~1.8× slower — 483 cycles vs 263 for a ten-element string loop with a method call per element.
  • No equivalent for some C++ tools — std::function with captures, dynamic_cast, and multiple inheritance have no Objective-Z counterpart. Introspection exists only as a C API (oz_isKindOfClass, oz_name).
  • Capturing blocks are rejected — a block that captures a local is a transpile-time diagnostic, where a C++ lambda would just work.

Method: all benchmarks on an nRF52833 DK (ARM Cortex-M4F @ 64 MHz) using the DWT cycle counter, overhead-calibrated, single inheritance only. The Objective-Z benchmark is pure Objective-C transpiled to C. Full per-section results, including the allocation, dispatch, lifecycle, refcounting and collections breakdowns, are in the project README.

Features

What the subset gives you

Everything that can be resolved at build time is in. Everything that would need unbounded runtime allocation is out.

Dispatch

  • Static dispatch — direct C function calls for non-protocol methods (12 cycles)
  • Compile-time dispatch — protocol calls resolved to direct calls when the receiver type is known (12 cycles)
  • Protocol vtable dispatch — const arrays in .rodata, zero RAM; 21-cycle polymorphic fallback for id receivers
  • Class methods — plain static function calls

Memory management

  • Compile-time ARC — scope-based retain/release, auto-dealloc, break/continue cleanup
  • Per-class slab pools — auto-sized from AST analysis, zero heap overhead
  • @autoreleasepool — scoped drain points for loops and worker threads
  • Foundation classes — OZString, OZArray, OZDictionary, OZQ31 with fast enumeration

Language

  • Categories — merged at AST collection time
  • @property / @synthesize — atomic and strong semantics
  • @synchronized — RAII spinlock via OZSpinLock
  • Blocks — non-capturing blocks become static C functions; __block variables are promoted to file scope
  • Fast enumeration — for (id obj in collection) via IteratorProtocol
  • Literals — @42, @3.14f, @YES, @[a, b], @{k: v}, and subscripting
  • Lightweight generics — typed collections
  • +initialize — auto-called before main() via SYS_INIT

Tooling & platform

  • Three-pass transpiler — Clang JSON AST → collect → resolve → emit → pure C
  • Platform abstraction layer — zero-cost static inline with Zephyr and host backends; every PAL function vanishes at -O1 and above
  • Zephyr-native primitives — k_mem_slab, SYS_INIT, k_spinlock_t, atomic_t; no libc malloc dependency
  • clangd support — auto-generated compile_commands.json
  • Architectures — ARM Cortex-M, Cortex-A, and RISC-V 32/64 (LLVM Clang required)

Quick start

Add it to a Zephyr application

Objective-Z is a Zephyr module. Four files and one CMake call.

  1. Add the module to your west manifest

    west.yml 
    manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos

  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: main
      import:
        name-allowlist:
          - cmsis

    - name: objective-z
      url: https://github.com/rodrigopex/objective-z/
      revision: main
      path: objective-z

  self:
    path: my_app

    Then run west update to fetch it.

  2. Point CMake at your .m sources

    CMakeLists.txt 
    cmake_minimum_required(VERSION 3.20.0)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(my_app)

# Transpile .m sources to C (ARC always enabled)
objz_transpile_sources(app src/main.m)

    The call accepts ROOT_CLASS (default OZObject), POOL_SIZES to override per-class slab sizing, and INCLUDE_DIRS for extra AST include paths.

  3. Enable the Kconfig option

    prj.conf 
    CONFIG_OBJZ=y

    CONFIG_OBJZ is the only option. It enables the transpiler pipeline and auto-selects STATIC_INIT_GNU. Foundation classes are included automatically and slab pools are generated for every class found in the AST.

  4. Write Objective-C

    src/main.m 
    #import <Foundation/Foundation.h>

@interface Sensor: OZObject {
    int _value;
}
- (void)setValue:(int)v;
- (int)value;
@end

@implementation Sensor
- (void)setValue:(int)v { _value = v; }
- (int)value { return _value; }

- (void)dealloc
{
    OZLog("Sensor dealloc (value=%d)", _value);
}
@end

int main(void)
{
    Sensor *s = [[Sensor alloc] init];
    [s setValue:42];
    OZLog("value=%d", [s value]);
    /* ARC releases s here -> dealloc fires */
    return 0;
}

    This becomes Sensor_setValue(self, v), Sensor_value(self) and an OZObject_slab_alloc() call in generated C. No Objective-C compiler or runtime is involved at build time — GCC compiles the output.

  5. Build

    west build -p -b mps2/an385 .

    Prerequisites: the Zephyr SDK and west, Clang 20+ for AST analysis, Python 3, and just if you want the repo's build recipes. Twelve runnable samples ship in samples/, from hello_world to zbus pub/sub and a request-response service.

Limitations

What it will not do

The subset is a deliberate trade. Know these before you commit a project to it.

  • Non-capturing blocks only — a block that captures a local variable is a transpile-time diagnostic error. Share state through a file-scope static or a __block variable instead.
  • __block becomes file-scope static — initialized once at program start, not on each entry to the enclosing function.
  • No typedef — use explicit types.
  • No @try / @catch / @throw — no exception handling.
  • No __weak — it panics at runtime. Break retain cycles with __unsafe_unretained or by clearing the back-reference before scope exit.
  • No dynamic dispatch for non-protocol methods — everything is resolved statically.
  • Single inheritance — an Objective-C constraint, not a transpiler one.
  • OZQ31 is Q31+shift — converts to int8/16/32 and float; no int64 or double.

The full list, including control-flow and collection details, lives in docs/LIMITATIONS.md.
