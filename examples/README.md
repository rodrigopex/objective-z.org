# Where the code on the site comes from

Two real, complete Objective-C files feed the page. Everything under each
`generated/` directory is the transpiler's own output for them — not written or
edited by hand.

```
hero/hero.m              first screen: a class plus a main() that uses it
hero/generated/          Thermostat_ozm.c (accessors), hero_ozm.c (main)
tour/thermostat.m        the scroll-linked tour's example
tour/generated/          thermostat_ozm.c, _ozh.h, oz_dispatch.*, OZTimer_*
```

Generated with objective-z v0.5.99.

The two examples live in separate directories on purpose: the tour emits
`thermostat_ozm.c` and the hero emits `Thermostat_ozm.c`, which are **the same
path** on a case-insensitive filesystem. Keeping them apart stops one from
silently overwriting the other.

## Checking

`tools/check_examples.py` verifies that every code pane on the page still traces
back to these files. It compares with whitespace removed and C line splices
rejoined, so reflowing a long line to fit a pane passes, while a renamed
identifier or a dropped line fails. Run it after touching either the page or the
examples.

## Regenerating

Both examples use Zephyr headers, so the AST dump needs a configured Zephyr
build's generated headers — the same ones the real build feeds Clang. From an
objective-z checkout, with `$AUTOCONF` pointing at a build's
`zephyr/include/generated/zephyr/autoconf.h` and `$ZFLAGS` holding the `-I`/`-D`
set from that build's `compile_commands.json`:

```sh
clang -Xclang -ast-dump=json -fsyntax-only \
      -fobjc-runtime=macosx -fobjc-arc -fblocks \
      --target=arm64-apple-darwin $ZFLAGS -Iinclude/oz_sdk \
      -DCONFIG_ARM=1 -DCONFIG_ATOMIC_OPERATIONS_BUILTIN=1 \
      -include $AUTOCONF \
      tour/thermostat.m > thermostat.ast.json
```

The tour example uses `OZArray`, so the Foundation implementations must be in the
same transpile unit — exactly as `objz_transpile_sources()` does it. Dump an AST
for each of `src/OZObject.m`, `OZString.m`, `OZArray.m`, `OZDictionary.m`,
`OZQ31.m` and `OZTimer.m`, then:

```sh
PYTHONPATH=tools python3 -m oz_transpile \
      --input <foundation ASTs...> thermostat.ast.json \
      --sources <foundation .m files...> tour/thermostat.m \
      --outdir tour/generated
```

Clang reports a handful of errors from the Zephyr headers themselves plus a
`mach-o section specifier` complaint on `ZBUS_CHAN_DEFINE` — host Clang is
standing in for the ARM target, and the project's own `.clangd` suppresses the
same ELF-vs-Mach-O attribute noise. None of them touch the Objective-C
declarations, and none reach the generated output.

## What each snippet on the site maps to

The hero pairs all of `hero/hero.m` with its accessors and its `main`. The rest
is the scroll-linked tour, ten steps generated by `tools/gen_tour.py` from exact
line ranges:

| Step | Source | Generated |
| --- | --- | --- |
| 1 | `ZBUS_CHAN_DEFINE` | the same macro, byte for byte |
| 2 | `@protocol Sensor` | `OZ_fn_read` function-pointer typedef |
| 3 | `Thermometer` interface + `-read` | `struct Thermometer`, `Thermometer_read` |
| 4 | `Hygrometer`, the second conformer | `OZ_PROTOCOL_RESOLVE_read` const table |
| 5 | `atomic` + `getter=isHeating` | accessors wrapped in `OZ_SPINLOCK`, `Thermostat_isHeating` |
| 6 | array literal and the timer block | retained stack buffer, `_oz_block_L0_C0` |
| 7 | `for (id sensor in _bank)` | iterator loop through `OZ_PROTOCOL_SEND_read` |
| 8 | `-spotCheck`, no memory code at all | `OZObject_release(spare)` injected before the return |
| 9 | `-shouldHeat` and no `-dealloc` | direct call; `Thermostat_dealloc` releasing three ivars |
| 10 | the C callback and `ZBUS_LISTENER_DEFINE` | only the message send rewritten |

Step 8 is the ARC demonstration: the method never mentions memory, and the
release appears at scope exit — before the `return`, resolved at compile time.
The hero shows the same thing in `main`.

## Callouts

A line the transpiler inserted — one with no counterpart in the source — is
marked in the generated column:

```html
<span class="add">    OZObject_release(...);<b class="add-tag">added by the transpiler</b></span>
```

The label is `user-select: none`, so copying the snippet does not carry it.

Both a single line and a whole block can be marked. In the tour, a line comes
from the `EMPHASIS` table in `tools/gen_tour.py` (which asserts the line exists);
a whole block comes from a fifth element on the block's line-range spec. The
generated `Thermostat_dealloc` is marked that way -- the class declares no
`-dealloc`, so the entire function is the transpiler's.

## Categories live in their own file

A category in the *same* file as its `@implementation` makes the transpiler emit
every method of the class twice — `Thermometer_read`, `Thermometer_dealloc` and
the category method all appear two times in one translation unit, which will not
compile. The shipped `hello_category` sample keeps the category in a separate
`Car+Maintenance.m`, and that works. That is why these examples have no category.

## A note on blocks and C callbacks

A block cannot be used as a `ZBUS_LISTENER_DEFINE` callback. The macro builds a
file-scope struct whose `.callback` member is a function pointer, and a block
literal is a block object — Clang rejects it outright:

```
error: initializing 'void (*)(const struct zbus_channel *)' with an expression
       of incompatible type 'void (^)(const struct zbus_channel *)'
```

That is an Objective-C type rule, not a transpiler limitation. Blocks work where
an API takes a block (`OZTimer`, `OZDefer`); C APIs taking function pointers need
a function, which is why the listener in the tour is a `static void` function
that sends a message to the object.
